===============================================================================
1. THE PIPELINE
===============================================================================
6c  raw article text --(1 extraction call + 1 review call)-> nary_graph_dedup.json
6d  entity types -> schema.org classes u minted types -> ..._typed.json
                                        + consolidation  ..._typed_consolidated.json   <- 6e READS THIS
6e  relation phrases -> schema.org properties u minted  -> ..._extended.json
                                        + consolidation  ..._extended_consolidated.json

Each notebook has TWO retrieval stages, both optional and independently switched:
  INLINE (Hook A)      per type / per phrase: e5 fetches TOP_K_MATCH candidates for the LLM.
                       With RERANK on, it fetches RERANK_FROM and a cross-encoder cuts to TOP_K_MATCH.
  CONSOLIDATION        once at the end: each minted term is shortlisted against its neighbours and
                       ONE LLM call merges synonyms / re-parents specifics.
                       With RERANK_CONSOLIDATE on, fetch RERANK_CONSOLIDATE_FROM, cut to CONSOLIDATE_TOP_K.

Two knobs decide WHICH POOL each stage sees (named from opposite directions):
  INLINE_VOCAB_CANDIDATES     False = schema.org only        True = schema.org + grown vocabulary
  CONSOLIDATE_INCLUDE_SCHEMA  False = vocabulary only        True = vocabulary + schema.org


===============================================================================
2. FILE NAMING — RUN_TAG / INPUT_TAG
===============================================================================
_sfx   = "_" + VARIANT                     identifies the variant, used to READ the previous stage
_osfx  = _sfx + "_" + RUN_TAG              everything a notebook WRITES
_isfx  = _sfx + "_" + INPUT_TAG   (6e)     which 6d run 6e READS

  6d RUN_TAG  ==  6e INPUT_TAG      <- MUST match, or 6e cannot find its input
  6e RUN_TAG                        <- names 6e's own outputs; differ it from INPUT_TAG to vary
                                       something in 6e alone (a prompt, a rerank setting) on top of
                                       an existing 6d run.

A tag must name a run that EXISTS: check results/<model>/art*/e2e/*_typed_consolidated.json

WHAT THE LOG SUPPORTS
  * MIXED consolidation is the single clearest win.  Folding a mint into a schema.org property both
    shrinks the vocabulary and lifts reuse, and vocab-only consolidation structurally cannot do it:
    24 merges / 18 into schema.org, vs 3 / 0.  Far larger than run-to-run noise.
  * Schema.org-ONLY inline (schemainline_rr) is NOT a win: inline vocabulary candidates let the LLM
    reuse its own earlier mints directly, which beats deferring that to consolidation
    (81 raw mints with the vocab inline vs 93 without).
  * The reranker helps relations, hurts types (see section 4b of the earlier analysis).

6. 6e PROMPT — WHAT WAS CHANGED AND WHY
===============================================================================
Relative to the prompt used for the "rr" run:
  1. removed "(their subject-type -> object-type signatures)" from the minting/naming bullet —
     it pointed at the signatures as naming MATERIAL, against the next bullet's "does not embed a
     subject or object".  Evidence: of 30 object-baked mints in "rr", 20 ended in a type appearing
     as the OBJECT in that group's OBSERVED_SIGNATURES (Event->Date became recordDate).
  2. split that bullet into IDENTIFY (the only step that looks at the instances) and NAME (the
     relation alone), stating that nothing from the instances is naming material, plus a generality
     test: the label must still make sense for arguments of completely different types.
  3. INSTANCE TEST tightened 1160 -> 697 chars: kept the orientation procedure, the leniency
     rationale and the accept/reject rule; dropped two restatements.
  4. orientation clause rewritten in the prompt's own arrow notation
     ("match subject -> object against domain -> range for as_is, or range -> domain for inverse").
  5. ALL-CAPS reduced 55 -> 26 tokens: kept only section headers, literal input field names, and the
     MUST/EXACTLY ONE invariant.
  6. OUTPUT prose replaced by 4 value-rule bullets (the JSON skeleton already gives the shape).

RESULT: object-baking did NOT move (38% -> 38%).  21 baked names disappeared and 17 new ones
appeared (teamHomeCity -> hasTeamHomeCity, burnedArea -> hasBurnedArea).  Four prompt attempts have
not shifted this rate; it looks like a job for a deterministic post-hoc check on minted labels
(reject a label whose suffix matches an observed object type, ask for a rename) rather than wording.

7. RUN-TO-RUN VARIANCE  (read before comparing anything)
===============================================================================
temperature=0 is greedy sampling, NOT determinism.  Hosted inference is batched, so float reduction
order shifts logits slightly and near-ties flip; a sampled reasoning trace amplifies it.  Thinking is
ON deliberately (thinking_budget=-1, ~120k thinking tokens per build) because it gives better
decisions.

MEASURED on this corpus — two runs, identical prompt / input / settings:
    raw minted properties        69   vs   91
    after consolidation          65   vs   67
    property decisions identical            45%
    same source (schema.org vs mint)        72%

So:
  * a single run is not evidence.  Repeat an arm ~3x under separate RUN_TAGs and report mean+range.
  * report POST-consolidation numbers — consolidation is deterministic given its input and absorbs
    most of the sampling noise (69/91 -> 65/67).  That robustness is itself a result worth reporting.
